Data Acceptance & Display Portal

A three-part web workflow developed for the B.Tech Electronics Engineering major-project cycle (B4, Session 2024–25). It collects project topic proposals, provides a central navigation page, and exposes submitted records through search and a public data table.

01 / PROJECT CONTEXT

Purpose and workflow

The system was created to support collection and public presentation of major-project topic submissions for B4. Students submit a topic name, a project description and details for one or two group members. The submitted information is sent to a Google Apps Script web app and subsequently made available through separate display interfaces.

The source repositories show three independently deployed frontend components: a collection form, a landing/navigation page, and a full-data table. The display landing page also links to a separate roll-number search application hosted at ashutosh1873.github.io/Data_Search_Major_Project_b4/; its source repository was not among the three ZIPs supplied for this review.

01 / INPUTStudent submission

Topic, 50+ word description, group size and member identity details.

02 / ROUTINGDisplay landing page

Choose roll-number search or the complete submitted-data table.

03 / OUTPUTSearch and review

Retrieve records, filter table rows and print the displayed data.

02 / COMPONENT ARCHITECTURE

Three repositories, three responsibilities

01. Data Collection — submission interface

The collection repository contains index.html, styles.css, script.js and script1.js. The active HTML page loads script.js. It collects the project topic and description, group size (one or two), and roll number/name for each member. Selecting two members reveals the second member fields and makes them required.

02. Data Display — navigation interface

The display repository contains a single landing page with two radio-button choices. Selecting “Search by AKTU Roll No.” redirects to the separately hosted search application. Selecting “Display Full Data Submitted Till Now” redirects to the full-table application. This component acts as a simple entry point rather than retrieving records itself.

03. Data Search / Table — record presentation

The third repository, Data_Search_Major_Project_Table_B4, loads records from a Google Apps Script endpoint when the page is ready. It creates table rows for topic, description, group size, and the two group members. A search field filters across all displayed cells, and a Print control opens a printable view.

03 / FORM VALIDATION & DATA SUBMISSION

Collection-side logic

  • Group-size-dependent fields: the second member section is shown only when the selected group size is two; its fields are toggled as required.
  • Roll-number check: JavaScript checks each submitted roll number against a predefined allowlist embedded in the client-side script.
  • Description length: the script counts whitespace-separated words and rejects descriptions below 50 words.
  • Payload structure: the request contains topic, description, groupMembers, a member1 object and either a member2 object or null.
  • Backend request: the active script sends a POST request containing JSON to a Google Apps Script web-app endpoint using the Fetch API.
  • User feedback: a processing overlay appears during the request; the interface then displays success, application-level error or network-error feedback.
Source-code distinction: the repository also contains script1.js, whose submission handler displays a late-submission message after validation. The supplied index.html loads script.js, not script1.js; therefore the late-submission handler is not part of the active page wiring in this source snapshot.
04 / DATA RETRIEVAL & TABLE FEATURES

Search, review and print

  • On DOMContentLoaded, the table script displays a loading overlay and fetches JSON records from a Google Apps Script endpoint.
  • After a successful response, it clears the table body and creates one row per record.
  • The table columns are Topic, Description, Group Members, Roll No 1, Name 1, Roll No 2 and Name 2.
  • The search function checks every cell in each row, case-insensitively, and hides non-matching rows.
  • The print function opens a new browser window, writes a table-oriented document and invokes the browser print dialog.

The code expects each returned record to have the topic, description, groupMembers and member1 fields, with member2 optional. The Apps Script server-side source and Google Sheet schema were not included in the supplied ZIPs, so the server-side data model and permissions cannot be independently verified from this review.

06 / ENGINEERING REVIEW

Considerations for a production version

  • Server-side validation: the roll-number allowlist is enforced in browser JavaScript in the supplied code. A user can bypass client-side checks, so equivalent validation should be applied by the Apps Script endpoint.
  • Safe rendering: the table currently interpolates fetched values into innerHTML. Using DOM text nodes or textContent for data values would reduce injection risk.
  • Data privacy: the full-table interface exposes student names and roll numbers to anyone able to access the public page and endpoint. Access should be restricted or personal fields minimised if the portal is reused.
  • Operational robustness: add clear empty-state and retry handling, validate the response shape, and document the Apps Script deployment permissions and versioning.

These are recommendations from reviewing the client-side source. The Apps Script code, spreadsheet sharing settings and deployment configuration were not supplied, so no conclusion is made about their actual server-side security.
